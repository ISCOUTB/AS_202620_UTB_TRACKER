# Diagrama de Contenedores (C4 - Nivel 2) - UTB Tracker

Los contenedores corresponden 1 a 1 con lo que existe en el repositorio: `App Móvil`
(proyecto Flutter, en la carpeta `frontend/`), `API Backend` (carpeta `app/` de este repo,
FastAPI), `Worker de mensajería` (módulo `app/messaging/worker.py`) y `Base de Datos`
(PostgreSQL en despliegue, SQLite en desarrollo/CI — ver `app/core/database.py`).

El `Worker de mensajería` es un proceso consumidor independiente (`python -m app.messaging.worker`)
que lee y escribe en la Base de Datos (específicamente en las tablas `mensajes_outbox` y
`notificaciones_procesadas`) para entregar las notificaciones de préstamos. En el despliegue
automático actual (`.github/workflows/ci.yml`), este worker no se arranca automáticamente y
debe gestionarse como servicio independiente.

Cada flecha entre contenedores está etiquetada con su **protocolo de transporte** y su
**formato de datos** por separado (actualizado en S7, contrato de API):

- App Móvil → API Backend: protocolo **HTTPS**, formato **JSON**, validado contra el contrato
  versionado en [`docs/contracts/openapi.json`](../contracts/openapi.json).
- API Backend → Base de Datos: protocolo **TCP**, formato **SQL** (vía el ORM SQLAlchemy).
- Worker de mensajería → Base de Datos: protocolo **TCP**, formato **SQL** (vía el ORM SQLAlchemy).

Las peticiones HTTP del cliente y las consultas SQL de la API son síncronas (petición/respuesta) — ver
[ADR-0003](../adr/0003-integracion-sincrona.md). La notificación de préstamos es asíncrona mediante el
patrón Transactional Outbox procesado por el worker — ver [ADR-0006](../adr/0006-mensajeria-asincrona-outbox.md).

> **Nota sobre Caché:** La estrategia de caché propuesta ([docs/datos/diseno-cache.md](../datos/diseno-cache.md))
> no se incluye como contenedor en este diagrama por tratarse de un diseño propuesto no implementado en el repositorio.
